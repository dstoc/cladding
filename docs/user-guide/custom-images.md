# Custom container images

Cladding can use a local or remote image for each runtime component, or build an image from a Containerfile. The `image` value is the image tag. When the component also has a `build` object, Cladding builds that tag.

```json
{
  "name": "myproject",
  "agent": {
    "image": "localhost/my-agent:latest",
    "build": {
      "containerfile": "containers/agent.Containerfile",
      "context": ".",
      "args": { "FEATURE": "enabled" }
    }
  },
  "nw_sandbox": {
    "enabled": true,
    "image": "localhost/my-sandbox:latest",
    "build": {
      "containerfile": "containers/sandbox.Containerfile",
      "context": ".."
    }
  },
  "fs_sandbox": {
    "enabled": true,
    "image": "localhost/my-fs-sandbox:latest"
  },
  "proxy": {
    "image": "localhost/my-proxy:latest",
    "build": {
      "containerfile": "containers/proxy.Containerfile",
      "context": "."
    }
  }
}
```

Add component settings to the config generated by `cladding init`; keep its existing `name` and default image fields. `containerfile` and `context` paths resolve from `.cladding/cladding.json`. If `context` is omitted, it defaults to `.cladding/`. Build `args` are string values passed to Podman as Containerfile arguments.

If `image` is omitted, `cladding build` generates a local image tag for the component. Cladding builds a shared image tag once. It reports an error if components use different build definitions for the same tag.

## Agent and network-sandbox images

After startup, Cladding installs the project's public Baffle CA certificate into the system trust store of the agent and enabled network sandbox. A custom image for either component must provide:

- `sh` and `cp`;
- a writable `/usr/local/share/ca-certificates/` directory; and
- `update-ca-certificates`, or a compatible command that adds certificates from that directory to the system trust store.

Cladding runs the certificate installation command with container UID 0. It does not start the workload as privileged; the process continues to use its configured unprivileged user. The default image sets `NODE_USE_SYSTEM_CA=1` so Node.js uses the system trust store. An application with a private CA bundle or a different trust store may need a separate import step. Certificate-pinned applications can reject intercepted connections.

## Proxy images

The default proxy image is built from Debian trixie slim and runs the Baffle binary that Cladding installs in the project tools directory. A custom proxy image must provide `/bin/sh`, GNU libc compatible with the pinned Baffle executable, `mkdir`, `chmod`, `dirname`, `sleep`, and `socat`. The startup script uses `socat` to verify the scoped socket bind. Keep `/run/baffle` sticky and writable so the proxy startup process can create a private control-socket directory. See [Proxy policy, CA, and credentials](../features/proxy/summary.md) for runtime details.

Custom network- and filesystem-sandbox images must provide `/bin/sh` and GNU libc 2.35 or later for the pinned Gantry executables. They do not need Bubblewrap or `gantry-supervisor` because Cladding selects Gantry's Direct backend.

## Execution options

Execution components use Podman's `--init` by default. Set `init` to `false` on an individual `agent`, `nw_sandbox`, or `fs_sandbox` object to omit that component's `--init` flag. Proxy containers always use `--init`.

```json
{
  "name": "myproject",
  "agent": {
    "init": false,
    "security_opts": ["unmask=/proc/*"]
  }
}
```

Without `--init`, the component does not get Podman's generic PID 1 zombie reaping and signal forwarding. Provide process supervision in the image or command when the workload needs those behaviors. Cladding passes each `security_opts` value as a separate Podman `--security-opt` argument.

The proxy and execution containers have different network, socket, and certificate access. See the [current runtime summary](../features/current-runtime-summary.md) before changing a component image's startup or filesystem layout.
