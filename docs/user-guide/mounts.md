# Mounts and workspace access

Cladding does not mount the host workspace by default. The agent and enabled network sandbox receive Cladding's project config, tools, and home directories. The filesystem sandbox receives read-only config and tools. Add an entry to `.cladding/cladding.json` when an execution component needs host files.

## Mount fields

Each entry in `mounts` supports these fields:

- `mount` (required): absolute path in the container.
- `hostPath` (optional): host path. Relative paths resolve from `.cladding/`.
- `volume` (optional): Podman volume name. It cannot be combined with `hostPath` or `type`.
- `type` (optional): `bind`, `readonly`, `copy`, or `tmpfs`. Host paths default to writable `bind` mounts. Named volumes use Podman's normal volume behavior.
- `size` (optional): size for a `tmpfs` mount, such as `1GiB`. The default size is `64MiB`.
- `targets` (optional): one or more of `agent`, `nw-sandbox`, and `fs-sandbox`.
- `ignore` (optional, defaults to `false`): remove a default mount at the same container path.

`readOnly` is not supported. Use `type: "readonly"` for a read-only host path. `bind`, `readonly`, and `copy` require `hostPath`. If neither `hostPath` nor `volume` is set and `type` is omitted, Cladding mounts an empty, read-only tmpfs. Cladding disables tmpfs copy-up, so this mount does not expose image files.

When `targets` is omitted, a mount applies to the agent and to `nw-sandbox` when it is enabled. Custom mounts for `fs-sandbox` must name it in `targets`. A target must be enabled in the selected project config.

## Give the agent read-only workspace access

This entry maps the directory containing `.cladding/` to `/workspace` in the agent. It does not give the other components access to those files.

```json
{
  "name": "myproject",
  "agent": {},
  "mounts": [
    {
      "mount": "/workspace",
      "hostPath": "..",
      "type": "readonly",
      "targets": ["agent"]
    }
  ]
}
```

Add this entry to the configuration generated by `cladding init` rather than replacing its generated image fields. `hostPath: ".."` is relative to `.cladding/cladding.json`, so it selects the project directory. Cladding adds an empty mask for the private `.cladding` directory inside a host-backed mount. Use the mount only for the files the component needs.

Cladding maps the invocation working directory into a container only when a configured host-backed mount for that target contains it. Otherwise, `exec` and `run` start in `/home/user` (Cladding's project home for the agent and network sandbox). The filesystem sandbox has no `/home/user` mount by default.

## Mount types

### `bind` and `readonly`

Both types mount the live host directory. Writes through a `bind` affect the host. A `readonly` mount prevents container writes to its source.

### `copy`

`copy` takes a snapshot of the host directory into a Cladding-managed disposable volume. The snapshot includes dotfiles and preserves symlinks and permission bits. Containers can change the snapshot without changing the host source. When one `copy` declaration targets multiple containers, they share that volume and see each other's writes. Later host changes do not appear in the running runtime. Cladding removes the volume on `down` or after `run` ends. Seeding takes time and disk space proportional to the source tree.

Cladding does not support `overlay`. Podman's normal overlay mount gives each container a separate writable layer, so it cannot provide shared writable state. Use `copy` for a shared writable snapshot.

### `tmpfs`

`tmpfs` is a disposable memory-backed mount. It cannot use `hostPath` or `volume`. Cladding accepts byte values and `K`, `M`, `G`, `T`, `KiB`, `MiB`, `GiB`, `TiB`, `KB`, `MB`, `GB`, and `TB` size units. Podman receives the limit in bytes. Cladding sets mode `1777` and requests ownership for the container's mapped user and group. One target uses a container tmpfs; multiple targets share a Cladding-managed tmpfs-backed volume. Its contents disappear when the runtime stops.

### `volume`

`volume` uses a Podman named volume. Cladding passes the name to Podman unchanged and does not remove this volume during `down` or after `run`.

## Examples

```json
{
  "name": "myproject",
  "agent": {},
  "nw_sandbox": { "enabled": true },
  "fs_sandbox": { "enabled": true },
  "mounts": [
    { "mount": "/workspace", "hostPath": "..", "type": "readonly", "targets": ["agent"] },
    { "mount": "/workspace/.cache/npm", "volume": "npm-cache" },
    { "mount": "/opt/data", "hostPath": "../data", "type": "readonly" },
    { "mount": "/workspace-snapshot", "hostPath": "..", "type": "copy", "targets": ["agent", "nw-sandbox"] },
    { "mount": "/tmp/cache", "type": "tmpfs", "size": "1GiB", "targets": ["agent", "nw-sandbox"] },
    { "mount": "/tmp/isolated" },
    { "mount": "/opt/nw-sandbox-only", "hostPath": "../nw-sandbox-data", "targets": ["nw-sandbox"] },
    { "mount": "/opt/fs-sandbox-only", "hostPath": "../fs-sandbox-data", "targets": ["fs-sandbox"] }
  ]
}
```

Default mounts can be replaced by an entry with the same `mount` path or removed with `"ignore": true`. Cladding applies private-state masks after configured mounts, so `ignore` cannot disable a mask. The private `.cladding` directory itself cannot be a mount source; `readonly` and `copy` also reject sources inside it. When a configured mount contains the project directory, Cladding masks `.cladding` at its corresponding container path.
